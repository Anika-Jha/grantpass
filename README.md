# GrantPass

### Prove you're eligible. Don't hand over your identity.

GrantPass is a privacy-preserving application system for education grants.

It lets an applicant prove eligibility using an Aadhaar-backed zero-knowledge proof without giving the grant office their Aadhaar number, name, address, photograph, or other unnecessary identity information.

The system also prevents the same person from submitting multiple applications during the same grant cycle using a persistent cryptographic nullifier.

---

## The problem

Kavita runs a ₹15,000/year education grant for first-generation college students across Vidarbha.

She received thousands of applications but encountered:

* duplicate applications
* coordinated application farming
* scripted submissions
* people applying more than once
* pressure to collect Aadhaar numbers to establish uniqueness

But Kavita does not actually need an applicant's identity.

She only needs to know:

> Is this a real eligible adult person, and have I already seen them this cycle?

GrantPass is built around that narrower question.

---

# What GrantPass does

An applicant:

1. Starts an application.
2. Receives a server-generated application challenge.
3. Generates an Anon Aadhaar zero-knowledge proof in the applicant flow.
4. Proves the required eligibility information.
5. Sends the cryptographic proof to GrantPass.
6. The server verifies the proof.
7. The server checks the application-specific signal.
8. The server checks the persistent nullifier.
9. A valid first application is recorded.

The server never receives the raw Aadhaar QR.

---

# Privacy model

### Never collected

GrantPass does not intentionally collect:

* Aadhaar number
* name
* date of birth
* address
* photograph
* phone number
* raw Aadhaar QR
* Aadhaar certificate
* Aadhaar XML
* wallet address
* device identifier

### What is stored

The application database stores only the information needed for grant processing and duplicate prevention:

* application ID
* grant cycle
* application challenge ID
* cryptographic nullifier
* application signal
* eligibility result
* application status
* timestamps

The nullifier is used to determine whether the same proof identity has already applied during the current grant cycle.

# Security boundary

The most important boundary in GrantPass is:

```text
Aadhaar
   ↓
Applicant device
   ↓
ZK proof
   ↓
Server
```

The server does **not** receive:

```text
Aadhaar QR
Aadhaar number
Name
DOB
Address
Photo
```

Instead it receives the zero-knowledge proof generated by the applicant flow.

The Anon Aadhaar SDK provides client-side proof generation and a core verification API for verifying serialized proofs. The project uses the `@anon-aadhaar/react` and `@anon-aadhaar/core` packages.

---

# Duplicate prevention

GrantPass uses an application-controlled nullifier seed.

The browser does not choose the seed.

The seed is configured by the application:

```text
NULLIFIER_SEED
```

The resulting nullifier is stored as a persistent record for the current grant cycle.

The database additionally enforces:

```text
cycleId + nullifier = unique
```

Therefore two requests attempting to create the same person's application cannot both succeed.

The server performs the duplicate lookup before recording the application, and the database uniqueness constraint provides a final race-condition barrier.

---

# Application-specific proof binding

A proof cannot simply be generated once and replayed against arbitrary application submissions.

The server creates a challenge:

```text
challengeId
signal
expiration
```

The signal is derived from:

```text
grant cycle + challenge ID
```

The applicant's proof is generated using that signal.

When the proof reaches the server, the server checks:

```text
proof.signal === storedChallenge.signal
```

A mismatch is rejected.

This binds the proof to the specific application attempt.

---

# Eligibility

GrantPass does not trust an applicant-submitted value such as:

```json
{
  "isAdult": true
}
```

Eligibility is evaluated from the outputs of the cryptographically verified proof.

The application therefore follows:

```text
verified proof
      ↓
revealed eligibility output
      ↓
eligibility decision
```

rather than:

```text
browser form
      ↓
eligibility decision
```

---
## Proof generation is performed locally in the applicant's browser using Anon Aadhaar. Depending on device performance, local ZK proof generation may take several seconds to over a minute.

```env
NEXT_PUBLIC_USE_TEST_AADHAAR="true"
```

### `DATABASE_URL`

Local SQLite database used for development.

### `NULLIFIER_SEED`

Application-controlled numeric seed used for the current grant cycle.

It must never come from the browser.

### `NEXT_PUBLIC_USE_TEST_AADHAAR`

Use:

```env
true
```

for local testing with Anon Aadhaar test data.

Use:

```env
false
```

for a production deployment configured for real Aadhaar proofs.

# Threat model

GrantPass assumes an attacker may attempt to:

* submit the same proof twice
* submit a proof generated for another application
* modify eligibility fields
* send a fake verification flag
* choose their own nullifier seed
* bypass the UI and call APIs directly
* race two application requests
* submit malformed serialized proofs
* replay an expired application challenge

The server therefore treats the browser as untrusted.

The UI is not the security boundary.

The API and database are.

---

# What GrantPass deliberately does not do

GrantPass does not use:

* email as a uniqueness identifier
* phone number as a uniqueness identifier
* wallet address as a uniqueness identifier
* IP address as a uniqueness identifier
* device fingerprinting
* browser cookies as identity
* Aadhaar number storage
* names as duplicate keys

The identity primitive is the cryptographic nullifier.

# Production considerations

Before using GrantPass with real applicants:

* deploy over HTTPS
* disable test Aadhaar mode
* use a production database
* protect volunteer access with authentication
* configure rate limiting
* configure security headers
* review logging
* ensure proof data is not accidentally logged
* review Anon Aadhaar production artifacts
* rotate grant-cycle nullifier seeds according to the application's identity policy
* conduct an independent security review

---

# Why this matters

The goal is not merely to replace Aadhaar storage with a hash.

A hash of an Aadhaar number would still make the Aadhaar number an application credential.

GrantPass instead asks the identity system to prove a statement:

> "I possess a valid Aadhaar-backed identity satisfying the required eligibility condition, and I have not already claimed this grant."

The grant office does not need to learn the underlying identity to answer that question.
